# Пиксельный движок: как устроен и как его менять (версия v3, 15.10.2026; правки 17.10.2026 — снимки без текста, один запуск Vision на страницу, Office из сканов; 11.2026 — многостраничный TIFF, код выхода при нераспознанных страницах, сбой сверки в постпроверке)

Конвейер разделён так, что движок распознавания меняется без правки остального. Исполнитель OCR-ветки — `dots_batch.py`, движок — `dots_engine.py` (общий модуль). Модули на Apple Vision: `orientation.py` (ориентация), `dewarp.py` (выпрямление фото), `coverage.py` (полнота и дочитывание), `barcodes.py` (QR), `crosscheck.py` (сверка имён и чисел, резервное чтение).

## Контракт OCR-ветки

`route.py` кладёт в `plan.json` строки `{"src", "orig"?, "rel", "out", "ext", "engine": "ocr", "pages", "force_ocr"?}`. Строка может нести `orig` — исходник, если в OCR отдана PDF-копия Office-файла (документ из сканов): заголовок .md и поле `orig` в `_ocr.json` берут имя исходника, а `src` в `_ocr.json` остаётся PDF (он нужен для чтения глазами и `page_features.py`). Исполнитель обязан: взять все строки с `engine == "ocr"` (старое имя `"marker"` тоже принимается), для каждой записать markdown по пути `out`, создав родительские папки, и рядом `<имя>_ocr.json`. Многостраничный TIFF — по странице на кадр (`route.py` считает кадры без PIL, `common.tiff_pages`). Страница без текста из-за сбоя (`mode` — `timeout` или `error` и нет `VISION_FALLBACK`; `common.unread_pages`) перечисляется в `failed_pages` в `_ocr.json`, а код выхода исполнителя тогда 1: файлы, где не распознана ни одна страница, уходят в `<план>.retry.json`, частично нераспознанные — в журнал и в чтение глазами. `workspace.py publish` не выдаёт документ, пока такие страницы не прочитаны глазами (`eyes` в `_ocr.json`).

Где лежат файлы: при обычной работе через `workspace.py` план, `.md` и `_ocr.json` находятся в рабочей папке запуска (`~/.local/share/convert-docs/runs/<id>/documents/`), а пользователю копируются только итоговые `.md`. Сбой самой сверки Vision (`crosscheck.error`) постпроверка выносит в «сверить», чтобы страница не выглядела проверенной.

**Сканы внутри PDF с текстом.** `route.py` находит страницы, где текста меньше 80 знаков, но есть картинка от 500 × 500 px (`pdftotext` по страницам и `pdfimages -list`). Текст документа делает быстрая ветка (обе её программы теперь пишут разделы `## Страница N`), а для сканов в план идёт отдельная OCR-строка с `only_pages`. `dots_batch.py` распознаёт только эти страницы и ставит текст каждой на место её раздела с пометкой `> ⚠ Страница без текстового слоя (скан)…`. В `_ocr.json` тогда `pages` — число распознанных страниц, `only_pages` — их номера, `doc_pages` — всего страниц. Раньше решение «текст или скан» принималось по первым пяти страницам файла целиком, и скан-приложение к иску молча выходило пустой страницей. Теперь такую страницу, если OCR её не читал, называет и постпроверка («ПУСТЫЕ СТРАНИЦЫ»).

**Формулы.** Простая арифметика из блока «Formula» (числа, знаки действий, `\text{…}`, пробелы LaTeX, `5{,}5`) выдаётся обычным текстом («2 034+350+360 = 4100 (тыс. руб.)»), чтобы числа находились поиском. Дроби, степени, индексы, корни и многострочные формулы остаются в LaTeX.

## Страница в dots_engine.py

```
картинка → [только по флагу --dewarp: Vision находит четырёхугольник листа (0,1–0,5 с), Core Image выпрямляет, если лист наклонён ≥ 1,5° или кадр шире листа]
  → Vision: ориентация (0.3 с) → поворот → ужатие до 4,7 Мпикс (2560×1840)
  → Vision читает ту картинку, что пойдёт в OCR, один раз (строки, уверенность) + page_features (синяя ручка, резкость)
  → снимок без текста (Vision < 3 строк, ≤ 5 областей текста, доля «бумажных» пикселей < 0,5, QR нет)? → в OCR не отдаётся: mode «empty», в .md строка Vision (NO_TEXT_SKIPPED)
  → промпт разметки dots.mocr, потоковая генерация, проверка петли каждые 96 токенов
      петля? → обрезать хвост, LOOP_DETECTED
  → JSON собрался и без петли → markdown по блокам (layout / layout-repaired)
  → иначе промпт «просто текст» (ocr), та же проверка петли
  → петля или лимит и там → запасные движки по очереди: Xiaomi-OCR-0 → HunyuanOCR-1.5 → GLM-OCR (second:<имя>)
  → строки Vision берутся из предпросмотра (второго запуска Vision нет): правдоподобные строки, которых нет в тексте, перечитываются по полосам (REREAD:n); кусок дописывается блоком в конец страницы, только если ≥ 15 % его слов есть в чтении Vision той же полосы
  → ни один движок не дал текста без петли → резервное чтение Apple Vision (VISION_FALLBACK)
  → QR-коды и штрихкоды → строки «‹QR› …»
  → (в dots_batch) сверка вторым чтением Vision (то же чтение, `cached_vision`): имена нечётко, числа ≥ 4 цифр и даты точно, цифра в цифру → пометка ⚠ и `crosscheck.numbers_near`
```

Детектор петли: точные повторы хвоста (как в chandra, но единицы короче 4 символов без букв — точки и подчёркивания бланков — не считаются) плюс сжимаемость последних 3 000 символов: zlib-коэффициент < 0,06 или доля уникальных 12-грамм < 0,05. Замер 15.10.2026 на 128 выходах семи моделей: все петли ≤ 0,056 / ≤ 0,081, нормальные страницы ≥ 0,074, типично 0,2–0,5. Лимит токенов 6 000 (нормальная страница 1 000–1 900, максимум на боевых прогонах без предупреждений 3 853).

Упор в лимит 6 000 токенов считается отказом страницы (нормальных страниц такой длины не бывает) и тоже запускает каскад. Параметры: `--no-skip-empty` / `DotsEngine(skip_empty=False)` — отдавать в OCR и снимки без текста; `DOTS_MODEL=` путь к снапшоту; `DOTS_SECOND=xiaomi,hunyuan15,glm` список запасных движков по порядку (пусто — выключить; `wevisdoc` — опция); `dots_batch.py --dewarp --no-rotate --no-reread --no-qr --no-check --second xiaomi,hunyuan15,glm`; выпрямление включается ещё `DOTS_DEWARP=1` или `DotsEngine(auto_dewarp=True)` (по умолчанию выключено).

## Что добавила v3 (вечер 15.10.2026)

- **Выпрямление** (`dewarp.py`; **по умолчанию выключено**, включается `--dewarp`, `DOTS_DEWARP=1` или `DotsEngine(auto_dewarp=True)`): Vision (`VNDetectDocumentSegmentationRequest`) находит четырёхугольник листа, `CIPerspectiveCorrection` натягивает его на прямоугольник. Условия: уверенность ≥ 0,5, лист не меньше четверти кадра, наклон ребра ≥ 1,5° или угол листа отстоит от края кадра ≥ 4 %. Выключено после замера 15.10.2026: полнота не изменилась (+0,004), на синтетическом фото оно потеряло ноль в 20-значном номере счёта, на одном скане из девяти стоило +100 с. При включении на замере выпрямилось 9 страниц из 21: 8 фото и один скан (таблица-сетка, ему это навредило — по замерам автора); на остальных восьми сканах картинка не тронута. Изгиб страницы (корешок книги) не лечится. Тон и шум (`CIDocumentEnhancer`) не трогаются.
- **Проверка полноты и дочитывание** (`coverage.py`): Vision читает страницу; строка, которой нет в тексте OCR и которая по орфографии (`NSSpellChecker`, ru) состоит из настоящих слов, считается пропуском; такие строки группируются в полосы (не больше четырёх), полосы перечитываются промптом «просто текст», новое дописывается блоком «Дочитано по областям» в конец страницы, но только если ≥ 15 % слов куска есть в чтении Vision той же полосы (`coverage.corroborated`, фильтр подтверждения). Замер фильтра: доля слов куска в чтении Vision не отделяет настоящий текст от выдумки, при пороге 0,3 из 8 перечитанных кусков не принят ни один, так что дочитывание на практике почти ничего не дописывает. Если пропущено ≥ 5 строк, а дочитать не вышло, страница попадает в раздел «Возможные пропуски» файла `_ПРОВЕРИТЬ.md`.
- **Резервное чтение Vision**: пустая страница или два зациклившихся прохода без помощи запасных движков → в конец дописывается чтение Apple Vision (≥ 8 строк, уверенность ≥ 0,45), без разметки.
- **QR-коды и штрихкоды** (`barcodes.py`, `VNDetectBarcodesRequest`): строки `‹QR› …` в конец страницы.
- **HunyuanOCR-1.5 как запасной движок** через `llama.cpp` (`llama-mtmd-cli`, GGUF Q8_0 + mmproj-f16, `repeat-penalty 1,08`): тот же ранний обрыв петли по потоку stdout. Быстрый (13–35 с/стр) движок без латиницы в словах; как основной не годится и «лучшей на кириллице» не является (эти цифры относились к версии 1.0). В mlx-vlm 0.7.8 модель не грузится.

- **Снимок без текста** (17.10.2026, `NOTEXT_*` в `dots_engine.py`): Vision < 3 строк, детектор областей текста (`orientation.text_rect_count`, VNDetectTextRectanglesRequest, ~0,1 с) ≤ 5, доля «бумажных» пикселей < 0,5, QR нет; любая неопределённость (нет Vision, ошибка детектора, нет numpy) — не пропускать. Условие «ink.blue_px < 150» из первого варианта не годится: синий цвет в кадре (стул, небо, краска) даёт 900–19 000 пикселей на 7 из 8 снимков помещения. Рукопись закрыта числом строк и областей (стр. 19 и 44 «Материала проверки»: 61 и 29 строк, 20 и 15 областей), почти пустая бумажная страница — долей «бумажных» пикселей (0,65–0,99 против 0,21–0,40 у снимков). Выкидывает OCR только для снимков вроде «фото помещения» (8 × 84 с впустую → 5 с). Режим страницы `mode: "empty"`, предупреждение `NO_TEXT_SKIPPED` (в `SILENT`), `engine: "apple-vision"`, `crosscheck` и `coverage` у такой страницы `null`.
- **Один запуск Vision на страницу** (17.10.2026): `_prescan` читает картинку один раз (раньше два: полнота и сверка); результат лежит в `PageResult.vision`/`vision_obs`/`features`/`notext`, идёт в `coverage.check(obs=…)`, резервное чтение, `dots_batch.cached_vision` → `crosscheck.check` и в `page_stats` (`vision_text`, `vision_conf`, `ink`, `sharp`, `notext`). QR берётся из предпросмотра, если уже декодирован.
- **Office из сканов** (`route.py`, 17.10.2026): текста после markitdown < 300 символов (буквы и цифры без ссылок на картинки и разметки), внутри картинки ≥ 30 КБ (`word/media`, `ppt/media`) → строка плана `engine: "ocr"`, `src` = `<имя> (из docx).pdf` рядом с .md, `orig` = исходник. С 17.10.2026 стоит LibreOffice: PDF делает `soffice --headless --convert-to pdf` (страницы как в Word, вместе с текстом); без soffice PDF собирается из картинок документа (`IMG_PDF`, venv markitdown: pymupdf + Pillow) в порядке появления в `word/document.xml` (pptx — слайды по порядку из `presentation.xml`), страница подобрана под рендер 200 dpi в родные пиксели, EXIF-поворот учитывается, картинки < 30 КБ пропускаются; короткий текст документа в PDF не попадает (в `note` об этом сказано). Если soffice появится, он пробуется первым (`soffice --headless --convert-to pdf`), этот путь не проверялся. Текст есть, но внутри картинки ≥ 100 КБ — остаётся markitdown, `note` = «внутри N картинок, их текст не распознан». Короткое письмо с картинкой подписи/печати: текста < 50 знаков — в OCR как выше; 50–300 знаков — в OCR только через soffice (его PDF несёт и текст) и при картинках ≥ 100 КБ суммарно, иначе остаётся текст markitdown (без soffice при картинках ≥ 100 КБ — с той же заметкой). Повторный запуск: PDF не пересобирается, если новее исходника и открывается (`pdfinfo`); .md с подписью «Распознано: N стр.» или ≥ 300 символов текста — готов; .md из одних ссылок на картинки при исходнике с картинками ≥ 30 КБ снова уходит в OCR; `<имя> (ПЛОХОЕ КАЧЕСТВО).md` — готов. Не проверено: .doc/.rtf/.odt/.ppt/.odp из сканов (нечем собрать тестовый файл), только отсутствие ложных срабатываний.

Пороги и откуда они взяты — по замерам автора 15.10.2026 (вечер) и 17.10.2026.

- **Запасные движки** (12 страниц эталона): HunyuanOCR-1.5 через llama.cpp 0,68 (28 с/стр, петля на 3 страницах), Xiaomi-OCR-0 0,64 (10,5 с/стр, петель нет), GLM-OCR 0,59 (23 с/стр, петля на 4). На 9 страницах без петли у Hunyuan она 0,82 против 0,69 у GLM — по правилу очередь xiaomi → hunyuan15 → glm. Hunyuan-1.5 — быстрый запасной движок без латиницы в словах, не «лучшая на кириллице» (это цифры версии 1.0: у 1.5 по русской странице 67,4 против 71,2 у dots.mocr) и не замена dots.mocr (0,74 с выпрямлением, 0,73 без).
- **Рукопись** (4 бланка): лучшая конфигурация — Qwen3.5-9B 8-bit с примером той же руки и выпрямлением, многоходовой формат: 0,57 (минимум 0,39); one-shot 0,55 (мин 0,38); zero-shot 0,40 (мин 0,06, зацикливается на «ооо…»); dots.mocr 0,37, Apple Vision 0,34; Qwen3-VL-8B 0,26–0,44 и неустойчиво. ≥ 0,50 на каждой странице не даёт ни одна конфигурация, поэтому ручной режим не предлагается и в скилл ничего не встроено. По статье 2609.37195 примеры там — строки, а не страницы (выигрыш Qwen3-VL-8B по CER всего 6–25 %, кириллицы в статье нет): путь дальше — нарезка бланка на строки по рамкам Apple Vision плюс примеры «строка → расшифровка», а не постраничный промпт.
- **Областной режим Xiaomi-OCR-0** (PP-DocLayoutV3 → кропы, как в статье): хуже целой страницы, 0,47 против 0,64 (8 фото 0,38 против 0,50), две страницы с петлёй; на размытых фото детектор областей находит 2–5 областей. Не кандидат.
- **Фасад с вывесками** (фото фасада из реального дела: 11 строк Vision, 152 с с петлёй и запасным движком) правилом «снимок без текста» не пропускается: текст на нём есть, и Vision читает его не хуже dots (у dots нет части названий на вывесках и госномера). Ослабить правило до «≤ 12 строк» нельзя: оно отрежет скриншоты кадастра.
- **Оговорки (перепроверка статей 15.10.2026):** цифры Xiaomi-OCR-0 в статье (Real5 Skew 94,5, таблицы 95,1) получены двухстадийно, у нас она шла целой страницей; WeVisDoc-4B мерился без системного промпта статьи (фото 0,80 могло быть занижено), в этот замер не входит.

## Почему dots.mocr, а не другие

По буквам русского печатного текста dots.mocr лучшая открытая модель (MDPBench 2026, табл. 3: edit 0,030 против 0,033 у PaddleOCR-VL-1.5 и 0,039 у Qwen3-VL-8B), по разметке страницы тоже (PageIoU 92,9). По странице целиком на русском выше PolyOCR-2.7B (85,4, кастомный ViT, в MLX нет), MonkeyOCRv2-B (80,1, своя архитектура, в MLX нет) и PaddleOCR-VL-1.6 (75,1, в MLX есть, но без своего конвейера разметки зацикливается на 10 страницах из 16). На фото с телефона dots.mocr теряет 13–15 пунктов — это слабое место, которое частично закрывают автоповорот и второе мнение.

## Замена движка

Добавить запись в `SECOND_OPINIONS` (репозиторий или локальный путь, промпт, repetition_penalty) и включить через `DOTS_SECOND`. Запись вида `"llama:<модель.gguf>|<mmproj.gguf>"` запускает движок через `llama-mtmd-cli` (так подключена HunyuanOCR-1.5). Чтобы заменить основной движок, нужен класс с методом `ocr_page(img) -> PageResult` и тот же `annotate()`; `dots_batch.py` других предположений не делает.
